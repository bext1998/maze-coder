# risk-driven-tdd

## 目標

用最小且有效的失敗證據驅動行為修改，保留 agent 對測試層級、工具與實作方式的判斷空間。

## 前置條件

- 先定義預期行為與最小可觀察驗證；是否改變行為不明時視為適用。
- 先確認既有測試基線，區分原有失敗與本次結果。
- 先定位根因，不得直接套用症狀修補；根因不明時先列候選原因並驗證，才進入修改。

## 執行流程

1. 建立能證明需求的最小驗證，並確認修改前因正確原因失敗。
2. 完成達成行為所需的最小完整修改。
3. 確認驗證通過並執行相關回歸；仍有價值時才重構。
4. 無法先建立自動化紅燈時，在實作前記錄原因、預期失敗的替代證據與未覆蓋風險；可用最小重現、既有命令、靜態檢查或人工驗證。

## 輸出契約

- 回報修改前失敗證據、修改後結果、相關回歸與殘餘風險。
- 未實際通過的驗證不得宣稱成功；基線失敗必須分列。

## 邊界

- 不強制每個內部步驟機械遵循 Red→Green→Refactor，也不指定框架、覆蓋率、mock 或命名。
- 不得因測試困難跳過驗證、忽略退出碼、弱化斷言或修改測試迎合錯誤結果。
